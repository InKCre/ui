## 起点与执行方式

当前分支为 `feat/ui-foundations-components`，HEAD 为 `c5b230af2461d401fa9dc3ac8d5b356c20b89c46`。工作区包含此前已验证但未提交的 B1/B2、C、D、E 改动。新实现应在执行开始时记录当时的工作区差异和生成基线，保留这些结果；此前 tarball 只能证明此前的实现，不能用来验收新的 Token 方案。

实施沿用现有 Style Dictionary、Sass、UnoCSS、Histoire、包契约检查和随包 Skill。设计关系可以由 Token 引用、少量局部 CSS 和使用说明共同表达；不建立统一公式语言或运行时求值器。文件格式默认保留当前 `type/value` 输入，除非真实工具互通需求证明本轮必须迁移。不同角色可以继续复用有意选择的基础尺度，不要求每个样式都增加 semantic 或 component 别名。

执行顺序是先建立 B3 的候选契约，再用 B4 检验并修订，最后进入 B5 的正式生成与迁移。B3/B4 允许针对失败场景局部往返；没有发生问题的角色不反复调整。B5 可以按已确定的设计领域分批评审，但最终交付必须保证新旧命名、生成物、组件和说明一致，不能发布一个只有部分消费入口兑现契约的版本。

## B3：明确设计角色、默认选择和变化边界

### B3.1 盘点实际决策和维护责任

从 [Token 源](../../tokens/inkcre.tokens.json)、[生成器](../../scripts/build-tokens.ts)、组件样式、Story 和 client-web 实际调用追踪使用关系。现有 237 个 `type/value` 叶节点不等于 237 个设计角色：例如 typography 的 121 个属性组成 11 个样式；颜色每个主题有 19 个 sys 条目。按角色归并盘点，不按叶节点生成大量维护表单。

盘点结果对每个实际使用的角色记录：用途与代表调用、当前默认、依赖和允许变化、维护位置、公开覆盖能力、处理结论。结论采用“保留／澄清／合并／拆分／新增／移除”；只有发现具体冲突时才新增或拆分，不能因暂时没有调用就删除已经公开的入口。

维护责任先采用以下起点：

| 责任位置 | 应作出的决定 | 不应隐含承担的决定 |
| --- | --- | --- |
| 共享设计规则 | 文本角色、颜色用途与合法配对、基础节奏、必要状态及主题映射 | 所有业务页面的布局、每个组件内部的几何计算 |
| Web 组件 | 内容排布、内部间距、文字与控件尺寸关系、状态表现 | 擅自改变宿主字体尺度或页面列数 |
| 宿主页面 | 容器空间、列数、页面留白、内容组织、采用哪个已支持模式 | 为弥补库缺陷重写字段和按钮内部样式 |
| 平台实现 | 将已确定的角色与行为要求转成平台能力 | 将 Web 的 CSS 表达式认定为所有平台共同格式 |

同时核对设计稿与代码之间谁维护什么。当前 [Token 导入脚本](../../scripts/prepare-token-update.ts) 会整份替换 `inkcre.tokens.json`，并自动生成 patch Changeset；必须明确新描述、角色与引用由 Figma 导出携带，还是由仓库维护，以及后续导入如何保留这些信息。默认保留单一规范源与受检查的导入边界，不先增加一套人工重抄的 Token 文件。

### B3.2 定义三类契约

每类契约应给出一个可直接使用的默认方案，再说明何时调整。具体命名、字号与系数在盘点和 B4 中确定；先保留现有品牌方向与常用尺度作为比较基线，不同时进行无关的视觉改版。

| 类别 | 必须确定的设计问题 | 推荐起点与待验证选择 |
| --- | --- | --- |
| Typography | 正文、标题、控件标签、辅助信息和代码文本分别是什么角色；字体家族由宿主继承还是由角色指定；字号、行高、字距、装饰中哪些属于同一组合；中文、英文和字体回退如何处理 | 明确 UI 字体和等宽字体的统一来源，让 Sass 与 Uno 使用相同规则。尺寸不足时优先检查换行、控件高度和布局，不先缩小文字。将 rem 字号、比例行高作为候选，保留固定值的合理用途；是否拆出 underline/mono 修饰以现有调用和组合需求裁定。 |
| Spacing 与尺寸 | 区分图标文字距离、字段内部留白、字段组间距、页面留白；哪些距离跟随文字，哪些跟随容器，哪些保持尺度；控件高度是固定高度还是可增长的最小高度 | 保留基础尺度作为默认选择。优先让含文字控件容纳其内容，由宿主负责页面空间变化。仅在实际场景需要时使用局部 em、有界变化或断点；不增加全局密度系数，不要求所有空白沿同一曲线缩放。 |
| Color 与状态 | 明确普通文本、弱化文本、动作前景、表面、边界、错误反馈及其合法配对；定义浅深主题下 normal/hover/pressed/focus/disabled/pending/selected 的适用范围和优先级 | 用实际前景背景组合判断颜色，不仅检查独立色值。澄清 text.primary 的含义及 muted/subtle 的区别；状态可以有意共享色值，但必须解释交互线索。仅对需要派生的关系使用混色；已有原生焦点表现若符合要求可以保留。 |

示例契约应具体到能写出验收步骤。以字段组为例：默认提供标签、输入和错误信息的文本层次；放大文本后控件应容纳文字，错误信息可以增加字段高度；相邻字段不能覆盖；窄容器中的列数由宿主决定；组件不能为保持单行自行缩小字体。这组要求允许用少量 Token 和组件 CSS 实现，不需要一个通用布局算法。

### B3.3 明确覆盖范围与求值时机

推荐以现有根级 light/dark/system 主题和少量有意公开的样式调整作为起点。构建时的品牌配置、运行时的主题选择、组件实例样式和用户字体设置分别记录，不能混称“支持主题定制”。

对每个承诺公开的覆盖入口，说明在哪个元素设置、影响哪些后代或组件、与主题和默认值如何叠加，以及预期传播到 Sass／Uno 哪些使用方式。根级主题继续遵循此前显式选择优先于系统的契约。局部多主题、全局密度和任意 ref 覆盖自动传播不作为默认新增能力；如有真实需求，再评估作用域及 Teleport 后的继承边界。

输出策略由这个决定反推：运行时可调整的角色应在需要共同响应的入口保留变量关系；只用于构建时的值可以解析为常量。断点等构建配置不应机械改成 CSS 自定义属性。Sass map 的构建值与 CSS 运行值可以职责不同，但必须明确哪种入口支持哪种覆盖。

**B3 交付与完成条件：** 形成一份精简的角色／处理清单、三类候选契约、维护及覆盖责任表，并给出 B4 的具体失败或比较场景。每个公开角色能回答“默认选什么、为何选择、何时变化、谁能改”；待验证选择有明确实验，不能仅留下“待定”。候选与实验结论记录在本工作包，最终契约在 B5 写入现有权威文档，不建立平行规范。

## B4：用代表场景验证和修订契约

### 场景与证据

优先复用现有 Form、Input、Button Story，以及 client-web 的 `apps/client-web/src/views/info-base/list/list.scss` 页面结构。实验使用隔离目录或临时消费页；正式实现阶段只把值得长期复核的场景合入对应 Story。页面实验可复现已读到的结构，不借此修改消费者仓库，也不新增 Card 组件作为前提。

| 场景 | 具体操作 | 通过依据 |
| --- | --- | --- |
| 表单内容与字体 | Input/Field/Form 组合，加入长中文标签、长英文及不可断字符串、多行错误；容器取 320/480/800 CSS px，并拖动检查布局转折处 | 标签、输入、错误和操作没有非预期覆盖或裁切；保留字段关联、键盘操作与提交行为；宿主和组件各自负责的换行、扩展或滚动有明确结果。宽度是实验样本，不自动成为新断点。 |
| 用户字体与缩放 | 默认字体、回退字体；分别检查根字号变化、浏览器缩放和文字放大至 200%，记录实际方法与环境 | 内容和功能仍可使用，控件能够容纳文字。根字号翻倍只证明相关单位依赖，不能等同所有文字已放大 200%；transform:scale 或截图缩放不作为文本缩放通过证据。 |
| 按钮颜色与状态 | primary/subtle/danger 在浅深主题下逐个检查默认、鼠标、键盘焦点、按下、禁用、加载；必要时放在其合法的不同表面上 | 前景背景配对可读，状态线索符合 B3，禁用和加载优先级清楚；不因新样式恢复误提交、重复动作等旧缺陷。对比度按最终合成颜色计算。 |
| 页面空间 | 相同页面内容放入窄侧栏和宽主区，比较原有留白、固定尺度与一个确有必要的响应候选 | 说明变化依据是 viewport 还是宿主容器；内容空间和层次有可观察改善。没有改善就保留较简单规则。若用容器单位，验证真实祖先容器及无匹配容器时的行为。 |
| 不同消费入口 | 同一字体角色、一个间距角色及一组颜色，分别通过公开 CSS、Sass helper 和 Uno 使用；设置一个 B3 允许的覆盖并再次测量 | 约定应相同的属性和变化结果一致；预期不同的构建值／运行值在指南中可解释。特别复核已发现的 label-lg-underlined 和 p-md 差异。 |
| AI 消费任务 | 仅给安装包文档与一个普通设置表单或页面需求，按指南完成组件、文本角色和布局选择；记录缺失信息和被迫猜测的地方 | 有默认实现可直接使用，不需要从源码找参数、不需要自己创造设计系数、不因同值而误用 Token。由当前执行者走读或作隔离消费实验；不为此新增 Agent 服务或擅自启动子代理。 |

以上不是全排列矩阵：先验证每个机制最相关的边界，再保留一组窄容器＋放大文字＋长内容，以及一组深色主题＋错误／加载的组合场景。发现新的交互风险时才扩展对应组合。

文字缩放依据 [WCAG 1.4.4](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)。普通文字的合法配对以 [WCAG 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) 的适用阈值验收，必要的非文本控件／状态线索参照 [WCAG 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)。这些是本次受影响场景的检查，不宣称整库已通过全部可访问性标准；视觉舒适度和信息层次仍需人工判断。

### 实验收敛与移交

每项实验只记录角色／假设、输入条件、候选规则、观察结果与取舍，附少量有代表性的截图或测量。出现裁切、不可读、失去操作入口或跨入口不一致时，回到对应契约修正。若两个候选均满足要求且没有明确视觉收益，采用更简单、上下文依赖更少的一种；涉及品牌方向或明显的产品取舍时，提供具体对照再请用户选择。

**B4 完成条件：** 每个计划进入正式源码的新规则都对应一个已解释的场景和观察结果；失败项已修订，未获证据支持的响应能力撤回。交给 B5 的是已选规则和可重复的验收步骤，而不是继续试验的系数清单。缺少真实消费者位置或特定浏览器时记录证据范围，不将临时页面称为该消费者已升级。

## B5：将已验证规则落实到源、输出和消费者

### B5.1 源与导入边界

按照 B3 的处理清单调整 `tokens/inkcre.tokens.json`。公开的共享角色保留必要描述和引用；组件内部计算继续留在组件 CSS。对主题配对、类型、单位、透明度和引用处理建立最小有效检查，复用 Style Dictionary 的现有解析能力，不再实现一个通用 Token 解析器。

更新 `scripts/build-tokens.ts`，使 Sass 与 Uno 从同一已定义角色取值，保留 B3 承诺的运行时关系。对字体家族、装饰、行高等属性采用一致的包含／继承规则，不以“输出更多属性”代替设计决定。颜色转换不得无声丢失 alpha，单位按已确定的类型处理，不能将所有数字统一理解为长度。

同步 `scripts/prepare-token-update.ts` 与 Token 更新工作流的必要边界：导入前验证目标格式、必要角色和引用；不让一个旧导出无声清除新契约。兼容的值更新与改名、删除、类型／语义变化应能区分；只有满足已定义兼容条件的更新才自动采用 patch，其余需显式发布分类或清楚失败。不增加通用语义版本推断引擎。若当前 Figma 导出确实无法承载必要信息，先用具体 payload 确认，再选择最小导入适配，不能默认堆叠多套源。

### B5.2 按设计领域迁移正式实现

推荐先落实 typography 和表单尺寸关系，再落实颜色／状态，最后迁移需要共享的新空间规则。每批同时修改其依赖的源、输出和组件；不能先整库改名、再逐个猜测组件该映射到哪里。

全量扫描当前 21 个组件以及本地可见的消费引用，按影响清单迁移。B4 的三类场景只用于先验证设计，不能被当作只修改三个组件的范围限制。重点复核 Switch 的字体和几何、Dropdown／Picker 的列表、Tooltip／Popup 的内容空间、AutoForm 和 JsonEditor 的长内容，沿用此前 C/D/E 的交互契约；第三方编辑器只调整本库拥有的样式接口。

旧入口按语义分类处理：完全等价的改名才考虑直接替换或短期别名；含义改变的角色给出新选择及人工复核步骤，不能用别名伪装兼容。`apply-font`、CSS 变量、Sass maps、Uno 类名与 package exports 都属于消费面，需要一起评估。别名若保留应只有一个方向，并写明移除时机，不维护无限双轨。

当前 `styles/README.md` 内容与包 README 重复，缺少其独立样式指南职责；B5 应恢复这一入口的具体内容，验证包内链接，避免再次建立自指或错误相对路径。不要将任务方案和实验历史复制进随包文档。

Skill 的推荐顺序是先使用组件及默认组合，再按设计角色选择已支持的调整；普通局部 CSS 可以保留，并说明哪些规则必须由库统一维护。新增说明优先进入现有 styling／recipe 输入结构。仅当现有生成器无法承载必要信息时作有界调整，完整 API 提取器改造仍归 F。

当前已有未发布的 major Changeset，但这不能替代本轮 Token 兼容说明。最终使用 `pnpm changeset` 记录本轮发布影响并与已有 major 发布合并审视；不在规划阶段 version、publish 或承诺下游已升级。正式消费迁移由 G 接续，B5 必须提供完整映射、已知调用和安装产物验证。extension registry 的位置缺口仍需 G 定位，不阻塞本仓库设计实验，也不能从验收中悄悄消失。

## 拥有的文件与检查边界

B3/B4 的规划和隔离实验由本工作包记录。实施启动后，B5 拥有 Token 源与生成器、Token 导入流程、Web styles、受影响组件样式及必要模板、对应 Story 和说明、Skill seed、Migration、Changeset，以及既有检查的最小扩展。生成物通过命令更新；无关组件模型、事件、schema 逻辑、依赖拆包、通用 CI 成本治理、共享文档托管块和消费者仓库均不随本方案自动修改。

验证采用现有行为边界，按以下顺序执行：

1. 源／生成器调整时先用隔离 `--root` 生成，核对类型、引用、单位、alpha 和旧新映射。正式源确定后运行 `pnpm generate`，查看全部生成差异。
2. 在 `scripts/check-package-contract.ts` 扩展既有公开入口 probe：保留变量完整性检查，增加选定字体角色的一致输出、必要零值／装饰重置、颜色 alpha 和一项公开覆盖关系的代表断言。以契约行为为断言对象，不快照全部数值或新增组件测试套件；不强求独立入口未承诺的行为一致。
3. 在 `scripts/prepare-token-update.ts` 既有 fixture 验证一次合法导入及会丢失必要契约的输入。预期失败不得被当作成功生成或兼容 patch；失败前已写入的源与 Changeset 也需避免留下半成品。
4. 受影响组件／Story 运行对应类型、lint、构建检查；用打包后公开 JS/CSS、Sass 和 Uno 入口重走 B4 已选场景，并抽查共享变化影响到的其他组件。B4 的临时原型通过不替代最终产物通过。
5. 本组交付前运行完整 `pnpm check` 和 `git diff --check`，核对 Changeset 分类及包内文档链接，将产物身份、浏览器环境、截图与未覆盖范围写回工作包。不在无新变化或失败时反复运行全套检查。

## 决策收敛与下一步

用户已经认可的原则和切片不再重新征求确认。执行时由维护者自行处理一般命名、CSS 写法和文件组织；以下决定先按推荐起点验证，只有出现会显著改变产品或授权范围的取舍，才提供具体结果供用户选择：

| 尚需确定的内容 | 推荐起点 | 决定位置 |
| --- | --- | --- |
| 默认字体来源与复合字体职责 | 统一 UI／mono 的来源，保证各入口的继承或指定行为一致；保留现有视觉方向作基线 | B3 候选，B4 中文／英文和回退字体比较 |
| 哪些角色支持运行时覆盖 | 保留根主题，逐项声明必要能力；不承诺修改任意 ref 都能自动改变全部后代 | B3 覆盖表，B4 传播实验 |
| 哪些间距或尺寸需要变化 | 先保障文字与内容可用，页面留白由真实容器场景决定 | B4 观察结果；无收益则保留固定方案 |
| Figma 与仓库的维护分工 | 单一规范源，导入受检查；先保留当前输入格式 | B3 责任表，B5 实际 payload 与导入 fixture |
| 旧公开 Token 的兼容处理 | 按真实语义分别迁移，major 中清楚说明；仅等价角色使用有限别名 | B5 调用盘点和 Migration |

B3 的盘点与候选契约、B4 的场景验证均已交付，结果见 [B4 已选规则](b4-validation.md)。B5 仓库内迁移随后已完成，结果见 [B5 实施记录](b5-execution.md)。用户在 B5 中要求停止继续处理 Firefox 原生 200% 文字放大专项，后续验收优先基础质量与默认消费契约。真实发送端和消费者升级仍需 G 核验。
