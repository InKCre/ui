## 参考与本项目判断

Vercel 的 [design.md 介绍](https://vercel.com/blog/how-our-agents-build-on-brand-pages-with-design-md) 发布于 2026-08-31。其公开文件服务于无法读取内部仓库的工具；设计指导、公开 CSS 和场景反馈共同工作。文章强调从具体使用场景与可观察的修正开始，人工判断设计质量，代码承担可以可靠检查的部分。

2026-09-13 读取的 [实际 design.md](https://vercel.com/design.md) 面向 Vercel 官方报告、提案、比较与决策页面，包含读者任务、信息组织、视觉规则、宿主集成和公开 CSS API。它的适用范围比通用组件库更具体，不能把其报告结构、品牌表现或 CSS 约束直接套到 InKCre。

另一篇 [仓库内 product-design 介绍](https://vercel.com/blog/teaching-agents-product-design-at-vercel) 发布于 2026-06-25，更接近维护 Agent 的工作：入口按任务引导读取权威资料，保留决定背后的原因，并区分已存在的实现与值得继续遵循的设计决定。它同样反对复制已有 API 和规则的权威来源。

本项目值得借鉴的是：把已认可的设计判断放到 Agent 能找到的地方，让稳定机制由组件和样式承担，再用真实任务检验说明是否有效。现有组件包、Story 和 Skill 已承担大量能力；当前收益不要求另建公开 CSS 服务、设计 Agent 服务或模型评测平台。

## 建议定位：共同的设计决策指南

建议使用根级 `DESIGN.md` 作为设计系统的长期入口，供人、消费者 Agent 和维护 Agent 阅读。它说明 InKCre 界面应保持什么、为何保持、默认怎么做、允许哪些变化，以及新增或修改设计能力时怎样判断责任。L3 承担这份知识的整理、发现与交付；其中已确定的 Token 和组件设计仍来自 L1/L2 的成果。

两类 Agent 共享规则，按任务读取不同补充材料：

| 读者任务 | DESIGN.md 应帮助作出的判断 | 继续读取的内容 |
| --- | --- | --- |
| 消费者构建或审视页面 | 信息如何分组，组件如何组合，何时沿用默认值，何时由页面布局解决 | 随包组件参考、配方、样式指南与公开 API |
| 维护者调整 Token、组件或指南 | 哪些关系必须保持，变化应放在共享角色还是局部实现，是否改变公开承诺 | Token 源、组件实现、Story、维护约定与迁移记录 |

维护者也需要理解消费方式，消费者也需要理解扩展边界；不维护两套独立设计原则。维护 Agent 的权限、命令和提交流程仍放在 AGENTS 中，DESIGN.md 只承担与设计有关的判断。

系统级指南可以帮助宿主判断主次、状态与组合，但不替 client-web 或 extension registry 决定业务导航、信息模型、权限和业务流程。具体产品有独立设计要求时，应由其仓库记录适用范围和差异。未来 Flutter／uniapp 可复用这里的意图和边界，Web 的 rem、CSS 变量、Teleport 等能力仍须明确平台适用性。

## 首版内容与表达方式

建议正文覆盖以下内容，不为每项预建独立文档：

1. **适用范围与判断顺序。** 从用户要完成的任务出发，明确内容可读、功能可用、状态诚实、设计关系一致等已有要求；说明产品责任和平台边界。
2. **视觉层级与默认选择。** 解释正文、标签、说明、标题的职责，文字与背景的配对，分组与空间关系。具体 Token 名称可以帮助定位，但不手抄全量值表，也不把尚未确定的品牌形容词写成规范。
3. **内容与上下文变化。** 保留 L1 已认可的字体、容器、主题和状态依赖；说明什么时候换行、增长或调整宿主布局，何时使用固定尺度，何时确有必要引入响应规则。
4. **组件组合与状态。** 给出表单、反馈、确认等常见场景的设计理由和少量正反例；完整 Vue 配方与各组件 API 留在既有随包参考中。
5. **维护和扩展判断。** 新需求先核对已有角色与组合；仅当职责和共同变化理由成立时增加共享能力。设计变化要说明影响范围、允许覆盖的责任和必要的兼容处理。

每条重要规则应能解释适用情境、建议行为、原因和允许的变化。用自然段与短例子表达，不规定每条都填一套表格。区分共同约束、可调整的默认选择和 Web 当前实现；尚未认可的提案仍留在工作包。不同情境的例外需要具体理由，不能用一句“保持灵活”消解规则。

例如，下面这些内容已经有 L1/L2 的设计或实现依据，可作为首版整理的材料，最终措辞仍需逐项核对：

| 情境 | 消费判断 | 维护判断 |
| --- | --- | --- |
| 说明文字在窄容器中变长 | 保留说明角色，先让内容换行并调整布局 | 控件不能依赖固定高度裁切内容；扩展能力与宿主布局责任分别处理 |
| 标签与说明当前字号相等 | 按用途选角色，不按像素值互换 | 只有职责和未来变化关系一致时才合并角色 |
| 表单正在保存或保存失败 | 保留动作含义、用户输入与明确反馈 | pending、error 与 focus 的责任分别成立，不让一个状态抹掉另一个状态的必要信息 |
| 页面希望有更宽留白 | 在宿主布局中表达页面需要 | 一页的数值差异不足以成为全局密度参数或新 Token 的依据 |

这些规则应约束后续实现，也应接受新证据修订。源码描述实际行为；如果它与已认可的设计要求不一致，应指出差异，再按任务范围修复或提出规则变更，不能仅因代码已经如此便把缺陷升为设计标准。

## 文档责任与现有内容整理

下面是建议的责任划分，确认实施前仍沿用现有入口：

| 内容 | 建议的权威位置 | 本轮之后怎样整理 |
| --- | --- | --- |
| 跨角色、组件与场景的设计判断及扩展原则 | 根级 `DESIGN.md` | 从已接受的 L1/L2 决定和现有指南提炼，保留理由、边界与短例子 |
| Token 名称、叶节点用途、类型、值与引用 | `tokens/inkcre.tokens.json` | 继续由规范源维护；DESIGN.md 不成为第二份 Token 表 |
| Token 格式、生成与受限导入 | `tokens/tokens.md`、`scripts/build-tokens.md` | 保留维护说明；共通设计判断移交 DESIGN.md 后改为引用 |
| Web 样式调用、覆盖范围与求值时机 | `packages/web/styles/README.md` | 保留 CSS/Sass/Uno 的具体调用与传播契约，通用判断减少重复 |
| 组件 API 与可运行用例 | 组件源码／声明、Story、生成组件参考 | F1 补事实；F2 让完整用例可检查；不用 DESIGN.md 手写一份接口 |
| 组件选型与完整配方 | `skill.seed.json` 与生成 Skill | 保留产品任务到组件的具体映射和配方，通用设计判断引导读 DESIGN.md |
| Agent 的加载时机、操作与验证步骤 | AGENTS、既有 Skill 入口 | 引导到所需资料，不重复设计规则和命令 |
| 兼容变化与升级步骤 | `packages/web/MIGRATION.md`、Changeset | 指向当前指导并保留版本迁移事实 |
| 候选、取舍历史与验证证据 | 本工作包 | 不随包分发，也不作为普通消费的必读材料 |

当前 [Token 指南](../../tokens/tokens.md)、[样式指南](../../packages/web/styles/README.md) 和 [Skill seed](../../packages/web/skill.seed.json) 已有重叠的角色、状态和默认组合说明。因此实施必须同时整理既有文档，不能仅新增一份完整说明。允许入口保留帮助读者理解的简短摘要，但同一规则只在一个位置裁决；不为消灭所有重复而建设文档抽取框架。

## 发现、版本与分发

建议只人工维护根级 `DESIGN.md`。维护入口由根／包级 AGENTS 明确 UI 设计、组件和 Token 工作何时读取它；纯构建或后端任务无需加载整份设计上下文。消费者经包 README 和现有 Skill 找到同一内容的随包副本，拟放在 `packages/web/DESIGN.md`，由既有生成链路同步，并纳入包文件清单与一致性检查。

正文应能独立解释设计判断；仓库源码路径和按读者区分的导航尽量留在入口文件。随包副本及其消费入口所需链接必须在安装环境可读，不能把“去生产者 tasks 目录看结论”留给消费者。若实际整理需要路径转换，只处理明确的少量入口，不设计通用 Markdown 编译器。

消费者读取与安装版本一致的指南，维护者读取当前 checkout 的指南。当前 major 改动尚未发布，不能把本地源码中的新规则说成 registry 中 1.4.0 的已有能力。未来可以再按真实的仓库外使用需要发布稳定网页 URL；本轮先完成仓库和安装包中的读取路径，不把文件名当成所有 Agent 都会自动加载的保证。

## L3 切片与顺序

保留现有 F1—F3、G1—G3 的责任；在 F 中补充 F0，不增设独立文档平台或新的任务层。

| 切片 | 交付与拥有范围 | 最小验收 |
| --- | --- | --- |
| F0 设计指南 | 确认本讨论稿后，整理正式 DESIGN.md 草稿、既有设计说明和维护读取入口；新增设计政策单列评议 | 两类读者能解释默认决定、允许变化和责任边界；已认可结论与新提案可区分 |
| G1 消费调查 | 只读核对 client-web、extension registry 的版本、入口、真实用例与 Agent 加载方式；核实 Figma 发送端 | 以证据限定 F/G 的范围；找不到的信息明确记录，不推定不存在 |
| F1 API 事实 | 源码、生成器与生成参考中的 models、类型、默认值、events、slots 及失败边界 | 安装包参考与公开声明一致，解析缺失不会静默伪装为完整 |
| F2 可检查配方 | 复用 Story 和公开入口表达少量完整消费任务，以 G1 证据选取 | 配方通过类型／构建检查，并能核对用户可观察状态 |
| G2 依赖责任 | 按 G1 的消费图调整 peer、运行时依赖、支持范围与发布说明 | 基础消费和可选集成的安装责任明确，不先预设拆包 |
| F3 + G3 交付闭合 | 在既有生成与包检查中纳入 DESIGN.md、Skill 导航、包内链接和最小安装；核对实际接入 | 无源码仓库也能完成约定消费；维护入口可读共同设计指南；区分本地验证与真实升级 |

先确认 F0 的定位和内容边界，再展开正式稿。G1 的只读调查可以在设计内容整理期间推进，其缺少某个仓库或 payload 的证据不阻塞共同原则的整理。F1/F2 沿用 L1/L2 已确定的组件契约；G2 和安装验证的具体改法待消费证据收敛。F3 在包交付阶段统一处理复制和链接，避免 F0 先建设一套新发布机制。

验收设计说明本身，先保留两个小任务的输入与结果：消费者从安装包完成普通设置表单及失败反馈；维护者处理长标签或新增文本用途，并说明为何复用、局部处理或提出新角色。核对是否还需要额外口头补充才能找对规则、是否违反既定设计关系。静态检查负责 API／文件完整性，设计与交互仍人工审视；两次演练只作为可用性证据，不宣称普遍提升 Agent 质量。

L4 继续暂缓平台实现；按用户既定边界，不重启 Firefox 原生 200% 文字放大专项。

## 确认结果

用户确认了三个相互关联的决定：采用供消费者与维护者共享的设计决策指南；以共同原则、可操作的默认选择和扩展边界为正文；只维护一个根级源，通过现有入口和包交付提供给两类读者。

用户已经确认上述具体安排并授权开始 L3。确认定位不等于无条件接受正式稿中新增的设计政策；整理时应区分既有结论的归档和新的设计主张。
