# UI 基础能力与消费契约整治

本工作包是本次 UI 基础能力审视、分组讨论和后续执行的唯一任务入口。长期使用指南仍由 README、AGENTS、Story 文档和随包 Skill 承担；工作包记录范围、决策、证据和执行状态，不替代这些文档。

## 目标与当前状态

目标是让现有 Web 消费者获得可靠的组件行为、设计语义、安装与开发体验，使消费者 AI 能通过随包文档正确选择和组合组件，使维护 AI 能找到并延续共同设计判断。未来 Flutter、uniapp 的扩展应复用已明确的设计契约，由真实消费场景驱动实现，避免提前建立平台框架。

用户要求按层、按组分别处理，并持续使用本 task packet。当前 **L0、L1 的 B1—B5、L2 的 C/D/E、L3 的 F0—F3 与 G2 已合入并正式发布为 @inkcre/ui-web@2.0.0**；G3 的 client-web／extensions 真实迁移在独立 worktree 和 [PR #104](https://github.com/InKCre/client-web/pull/104) 中验证。G1 的 extension registry 独立 UI／Figma 发送端仍待定位，L4 平台实现暂缓。

功能与版本分别经 UI [PR #43](https://github.com/InKCre/ui/pull/43)、[PR #44](https://github.com/InKCre/ui/pull/44) 检查后合入。正式发布、产物身份和消费者关联见 [发布与真实迁移](release-and-consumer-migration.md)。本地历史提交和验证证据保留在后续执行记录中；“未提交／未发布／消费者原状”仅描述各阶段结束时的状态。

## 持续使用规则

开始每轮工作前，读取本文件和当前组，确认最新用户指示、代码基线、已完成事项与未决选择。新的用户纠正、范围决定和授权在同一轮写回工作包；保留已有授权，不重复询问。

每个执行切片记录目标行为、拥有的文件或模块、非目标、兼容性影响和最小充分验收方式。实际需要展开某个复杂切片时才增设执行记录，不为所有组预建空文档。状态按“待讨论 → 待执行 → 执行中 → 已验证”推进；存在具体阻塞时记录缺少的条件。“已验证”不等于已提交、已发布或消费者已升级。

结束每轮工作时更新当前组的结果、证据、遗留事项和下一步。发现跨组问题时记录一次并链接归属组，不在多个组复制修复方案。任务结束时把长期有用的结论更新到原有权威文档，工作包保留执行证据。

每个已启动切片应完成必要源码、相关文档、生成物、适用 Changeset 和验证。提交、跨仓修改及发布按用户已授予的范围处理。仅编辑本工作包不改变包消费行为，不创建发布 Changeset。

## 共同约束与完成标准

- 保留现有组件清单、生成链路、随包 Skill、Histoire、Changesets 和源码联调中已证明有用的能力；每次删除或新增机制都要对应具体成本或缺口。
- 区分缺陷修复与 API 调整。按钮默认提交行为、模型值类型、取消语义、依赖范围等变化，都要先核对真实调用和兼容影响，再决定迁移方式与版本级别。
- Token JSON、组件源码与 manifest、人工维护的选型指导分别拥有自己的事实；生成物不直接编辑，也不增设另一份手工 API 权威。
- 按现有组织验证政策选择证据。本仓库目前不设自动化单元／组件套件；静态检查不能证明的交互，应以具体黑盒旅程验证，只有收益明确的行为才讨论持久自动化。
- 不把源码联调成功视为已发布产物可用，不把 Story 构建成功视为交互或视觉正确，不把 Skill 结构校验视为内容完整。
- 不提前建立多端 renderer、插件系统、通用表单框架、全量浏览器矩阵或额外 AI 文档服务。

组级完成要求是：该组确定的行为和契约已经兑现，有对应证据，文档与产物一致，兼容与下游事项明确。H 的暂缓实现不阻碍当前 Web 整治完成；如果启动非 Web 交付，再明确新增范围。
